# 标定管线 — 设计详解

为什么 v1.5 要先建三张表再动 CurveShaper、负载电池如何落到每个频率
档位、求解器怎样选出最优网格。日常使用见 [QUICKSTART.md](QUICKSTART.md)；
完整手册见 [README.md](README.md)。

其他语言 / Other language: [English version](../en/CALIBRATION.md)

---

## 1. 核心思想：先建模，再应用

CurveShaper 的 5×3 网格本质上是三组物理关系的乘积空间：

| 表 | 对应 CS 网格含义 |
|---|---|
| **频率-电压表** —— 各频段稳定频率 vs 电压偏移 | 固定温度下的 5 个行（Min/Low/Mid/High/Max） |
| **频率-温度表** —— 频段达到的频率 vs Tctl | 同一行在 3 个温度列上的表现 |
| **电压-温度表** —— 稳定边界随温度的漂移 | 每 (行, 列) 组合的边界 |

三者都是同一个三维曲面——最大稳定频率 F(V, T)——的二维切片。经典
搜索是盲测这个曲面，一次一格（每格 3–7 次重启 × 15 格 × 精调遍数）。
管线则是*系统性*采样——7 次统一偏移重启同时填满三张表——然后解出
网格。

两个性质让这条路成立：

1. **稳定域内，频率随电压偏移下降单调上升**（已在硬件上实测证实）。
   所以最优点*就在*稳定边界上，而不是曲面内部的某个极值——找最优点
   是边界检测问题，不是搜索问题。
2. **CS 自己就在锚点之间做线性插值。** 标定数据不需要正好压在锚点上，
   只需要沿频率轴铺开，拟合会覆盖其余部分。

## 2. 频率点怎么确认：归因，而非指定

CS 的行由 CPU 自己选——内核*实测*频率决定哪一行的偏移有权重。我们
无法"设定"某一行，只能"落到"它上面。两个机制解决这个问题：

**差分归因实验**（一次性，约 5 次重启）。每次重启把一行 CS 设为 +30，
与 offset-0 基线电池对比；频率发生移动（≥100 MHz，方向不限——敏感度
才是信号）的工况就归因给该行。单行 +30 的暂存实验已经验证了半张映射：
Min +30 移动了空闲频率，High/Max +30 移动了热态全核频率。

**按实测频率归行，绝不按工况名称归行。** 欠压会把频率推高；原本落在
Mid 频段的窗口可能飘进 High 频段。电池数据永远带实测频率，求解器按
工况映射 + 实测值归行，工况名称只当先验用。这个残差偏差正是"格子互相
影响"现象——残差精修引擎就是为它准备的。

## 3. 负载电池：把窗口放到频率轴上

所有负载手段都是运行时生效的，所以重启只花在 CS 偏移变更上；频率轴
扫描在每次开机内是"免费"的：

| 工况 | 机制 | 落点（9900X3D 参考） |
|---|---|---|
| `idle` | 无负载 | < 3 GHz 下沉 + 低温空闲 boost —— Min 行 |
| `peak` | Python 忙循环绑到一个逻辑核 | ~5.3+ GHz 单核 boost —— Max 行 |
| `allcore` | y-cruncher VT3（burn 回退），全线程 | ~4.9–5.1 GHz 热态持续 —— High 行 |
| `mid` | 全核负载 + `powercfg` PROCTHROTTLEMAX = 99% | ~4.4 GHz（关 boost，基础频率）—— Mid 行 |
| `low` | 全核负载 + PROCTHROTTLEMAX = 75% | ~3.3 GHz —— Low 行 |

PROCTHROTTLEMAX 是纯 Windows 电源管理：立即生效、零驱动依赖。如果
某个电源计划无视它，mid/low 窗口的频率会仍是全核 boost 水平——求解器
会检测到（该窗口频率没有比全核窗口低 ≥150 MHz），把工况标记为"无效"，
保守地复用全核边界。

每个窗口记录 `(偏移, 工况, 频率, 温度, 稳定性, WHEA)`。温度由后台
线程以约 2 Hz 从 Tctl 采样（SMN `0x59800`，经探测工具读取），F-T 和
V-T 表的温度轴就这样免费获得。全核窗口兼任该档位的稳定性门槛
（y-cruncher 判定 + 分窗口 WHEA 统计）。

一次会话约 10 分钟；每个偏移档位一次重启 × 7 档 ≈ 全部标定 70–80 分钟。

## 4. 求解器：边界 + 裕量 + 上限

对每个工况（映射到它的 CS 行）：

```
boundary     = 扫描中见到的最深稳定偏移
chosen       = boundary + MARGIN                # 向零回收
chosen       = max(chosen, boundary)             # 绝不比已验证的更激进
chosen       = min(chosen, MAX_VOLTAGE_OFFSET)   # 电压上限
chosen       = max(chosen, MIN_SAFE_OFFSET)
if 预测频率(chosen) > MAX_FREQ:                  # 沿 F-V 曲线回收
    chosen = freq 恰为 MAX_FREQ 的偏移           # 向零截断
if 预测温度(chosen) > MAX_TEMP:                  # 警告：欠压降温，
    ...                                          # 但更深偏移已不稳定
```

几个值得知道的细节：

- **唯一的自由参数是 MARGIN。** 标定时的稳定证据（几分钟 y-cruncher）
  弱于数周长期运行，所以网格刻意停在边界内侧 MARGIN 个偏移单位
  （默认 10 = 2 个扫描步长）。验证失败就加大裕量重新推导——表不变，
  代价是一次重启，不是重新标定。
- **频率上限通过反解执行**：求解器找到插值频率恰好等于上限的偏移，
  向零截断，保证线性插值误差永远不会越过上限。
- **温度上限达不到时是报告，不是修复。** 欠压确实降温，但在稳定边界
  上更深偏移已不可能——这个警告的意思是"需要更好的散热"，而不是
  "换个偏移重试"。
- **退化数据保守处理**：从未稳定 → 钉在电压上限；扫描从未失稳 → 标记
  无界；矛盾的崩溃残留（比稳定点更浅的失稳行违反单调性）→ 丢弃。
- 每行的偏移写入**全部三个温度列**。统一偏移扫描暂时分不开列——这是
  残差精修首先能改进的地方。

## 5. 验证，必要时精修

推导网格会被真正重启进去测量（v1.4 只暂存最终网格、不测）。结果：

- **稳定，频率符合预测** → 完成。
- **失稳** → 加大 MARGIN 重新推导（表不变）。
- **某个频段频率低于预测** → 二维表没捕捉到的交叉项；运行
  *refine current grid*——经典逐格引擎从推导值出发，只吃残差。

## 6. 崩溃韧性

每个窗口之后状态都会持久化。如果 Windows 在电池中途死机：

- 下次开机检测到状态 `battery_running`；
- 每个没跑到的窗口被记为该偏移**失稳**（在暂存网格下死机本身就是
  稳定性判定）；
- 该档位稍后重跑以获得真实测量，求解器的单调性过滤会丢弃矛盾的
  崩溃残留。

## 7. 已知局限

- **Mid/Low 锚点是近似。** 行锚点频率是熔丝值，不可读取；限频窗口
  落在频段*附近*而非正中。CS 对锚点做插值，拟合表能覆盖差距。
- **列没有分开**：统一扫描每行只有一个偏移（三列同值）；分列精修是
  后续工作/精修引擎的职责。
- **归因假设每个工况一个主导行。** shaper 影响场互相重叠会模糊边界；
  精修一遍吸收误差。
- **温度是观测的，不是受控的** —— 两个自然锚点（冷空闲、热负载）
  覆盖 CS 的冷/热列；中间列靠插值。
